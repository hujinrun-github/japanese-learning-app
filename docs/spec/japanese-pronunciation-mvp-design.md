# 日语发音纠正第一阶段 MVP 设计方案

## 1. 背景与目标

本方案面向日语学习产品的第一阶段发音纠正能力，目标是在成本尽量低的前提下，提供相对有效、可解释、可迭代的口语跟读反馈。

第一阶段不追求完整专业音素级评分，也不做开放式 AI 对话，而是优先解决日语学习者最常见、最容易产品化检测的问题：

- 长音不足
- 促音不明显
- 拨音被吞掉
- 清浊音混淆
- 拗音拆读
- 拍 mora 节奏不稳
- 漏读、多读、错读

核心产品定位：

```text
日语固定句子跟读纠错 + 日语节奏/长短音专项反馈
```

## 2. 第一阶段产品范围

### 2.1 支持场景

第一阶段只支持固定文本跟读：

```text
用户看到一句日语
→ 听标准音频
→ 跟读录音
→ 系统分析录音
→ 返回评分、错误定位、中文纠正建议
→ 用户重练
```

### 2.2 支持能力

| 能力 | 示例 | 第一阶段处理方式 |
|---|---|---|
| 完整度检测 | 漏读、多读、错读 | ASR 文本比对 + 目标文本对齐 |
| 长音检测 | おばさん / おばあさん | mora 时长 + ASR 差异 |
| 促音检测 | きて / きって | 促音位置停顿/闭塞时长 |
| 拨音检测 | こんな、ほんとう | 拨音 mora 是否存在、时长是否过短 |
| 清浊音检测 | か / が、た / だ | 假名差异 + ASR 混淆规则 |
| 拗音检测 | きよ / きょ | 假名序列与 mora 数量比对 |
| 拍节奏检测 | がっこう、きょう | mora 时长比例、异常停顿 |
| 流利度检测 | 停顿太多、语速太慢 | 停顿数量、语速、连续性 |

### 2.3 暂不支持能力

- 开放式 AI 语音对话
- 实时打断式纠音
- 完整音素级评分
- 高低重音精细评分
- 句子自然语调评分
- 真人级口型/舌位诊断

高低重音可以作为第二阶段能力加入，第一阶段只预留数据结构和扩展点。

## 3. 总体技术架构

```text
前端
  - 句子展示
  - 假名展示
  - 中文释义
  - 标准音频播放
  - 录音/重录
  - 结果展示

后端
  - 音频上传
  - VAD 去静音
  - ASR 转写
  - 文本规范化
  - 日语 G2P / mora 分析
  - Forced alignment
  - 规则评分
  - 中文反馈生成

数据层
  - 课程文本
  - 标准音频
  - 用户录音
  - 评测结果
  - 用户错音历史
```

## 4. 推荐开源组件

| 模块 | 推荐组件 | 用途 |
|---|---|---|
| ASR | faster-whisper / whisper.cpp | 用户录音转写 |
| VAD | Silero VAD | 去除头尾静音、检测有效语音段 |
| 对齐 | Montreal Forced Aligner / WhisperX | 获取词、音素或近似时间戳 |
| 日语 G2P | pyopenjtalk / OpenJTalk | 文本转读音、音素、mora 信息 |
| 假名处理 | jaconv / pykakasi | 日语文本标准化、假名转换 |
| 音频分析 | librosa / praat-parselmouth | 时长、能量、停顿、后续音高分析 |
| 反馈生成 | 模板规则 / 低价 LLM | 生成中文纠错建议 |
| 标准音频 | 真人录音 / 预生成 TTS | 跟读参考音频 |

推荐第一阶段优先组合：

```text
faster-whisper
+ Silero VAD
+ pyopenjtalk
+ MFA 或 WhisperX
+ 规则引擎
+ 模板反馈
```

如果团队工程资源有限，可以先不接完整 MFA，先用 WhisperX 或 Whisper 时间戳做粗粒度对齐，P1 再引入 MFA。

## 5. 核心处理流程

### 5.1 内容预处理

课程内容入库时提前处理：

```text
日语原文
→ 文本标准化
→ 假名转换
→ mora 序列生成
→ 音素序列生成
→ 标准音频绑定
→ 标准节奏信息生成
→ 入库
```

示例：

```json
{
  "sentence_id": "jp_001",
  "text": "がっこうへ行きます。",
  "kana": "がっこうへいきます",
  "mora": ["が", "っ", "こ", "う", "へ", "い", "き", "ま", "す"],
  "focus_points": ["sokuon", "long_vowel"],
  "translation_zh": "去学校。"
}
```

### 5.2 用户录音处理

```text
用户录音
→ 格式转换，统一采样率
→ VAD 去除无效静音
→ ASR 得到转写文本
→ 文本规范化
→ 与目标文本比对
→ Forced alignment 获取时间戳
→ 输出中间分析结果
```

音频建议统一为：

```text
16kHz
mono
wav/pcm
单句 3-15 秒
```

### 5.3 规则检测

规则引擎输入：

```text
目标文本
目标假名
目标 mora 序列
用户 ASR 结果
用户音频时长
对齐后的音素/片段时间戳
```

规则引擎输出：

```text
错误类型
错误位置
严重程度
置信度
中文反馈建议
```

## 6. 日语专项规则设计

### 6.1 长音检测

典型错误：

```text
おばあさん → おばさん
こうこう → ここ
せんせい → せんせ
```

检测逻辑：

- 目标 mora 中存在长音相关结构，如 あ段延长、い段/え段长音、う段长音。
- 对齐后目标长音 mora 的时长明显短于相邻普通 mora。
- ASR 或假名比对结果缺失对应长音。
- 若标准文本为长音词，而用户识别结果更接近短音词，则提高错误置信度。

反馈示例：

```text
「がっこう」最后的「こう」需要读满两拍，不要读成短短的「こ」。
```

### 6.2 促音检测

典型错误：

```text
きって → きて
がっこう → がこう
まって → まて
```

检测逻辑：

- 目标 mora 中存在「っ」。
- 在「っ」位置附近应有短暂停顿、闭塞或能量下降。
- 如果对应区间过短，或 ASR 结果缺失促音，则判断促音不明显。

反馈示例：

```text
「がっこう」里的「っ」需要有一个短暂停顿，可以理解成先收住一拍再发「こ」。
```

### 6.3 拨音检测

典型错误：

```text
ほんとう → ほとう
こんな → こな
せんせい → せせい
```

检测逻辑：

- 目标 mora 中存在「ん」。
- 对齐后「ん」区间过短或缺失。
- ASR 结果缺失「ん」或识别为相邻音节。

反馈示例：

```text
「ほんとう」里的「ん」不要吞掉，需要单独占一拍。
```

### 6.4 清浊音检测

典型错误：

```text
が → か
ざ → さ
だ → た
ば → ぱ / は
```

检测逻辑：

- 目标假名和 ASR 假名存在清浊对应差异。
- 维护清浊混淆表。
- 如果只发生清浊差异，而其他 mora 基本一致，则定位为清浊音问题。

混淆表示例：

```json
{
  "が": "か",
  "ぎ": "き",
  "ざ": "さ",
  "だ": "た",
  "ば": "は",
  "ぱ": "ば"
}
```

反馈示例：

```text
「が」听起来有点像「か」。读浊音时声带要振动，不要只发成清音。
```

### 6.5 拗音检测

典型错误：

```text
きょ → きよ
しゃ → しや
りゅ → りゆ
```

检测逻辑：

- 目标中存在「きゃ、きゅ、きょ、しゃ、しゅ、しょ」等拗音。
- 目标拗音应作为一拍处理。
- 如果 ASR 或假名比对显示被拆成两个普通假名，则判断为拗音拆读。

反馈示例：

```text
「きょ」是一拍，不要拆成「き」和「よ」两拍。
```

### 6.6 拍 mora 节奏检测

检测目标：

- 日语每个 mora 节奏相对均匀。
- 长音、促音、拨音都要占一拍。
- 学习者常见问题是把长音、促音、拨音读得太短。

检测逻辑：

- 估算整句平均 mora 时长。
- 每个普通 mora 的时长与平均值比较。
- 长音、促音、拨音如果显著低于阈值，则判定节奏问题。
- 异常长停顿计入流利度扣分。

反馈示例：

```text
这句话的拍子有些不均匀。「っ」「う」都需要占一拍，可以先慢速按拍读。
```

## 7. 评分设计

第一阶段采用 100 分制，总分由四部分组成：

```text
总分 = 完整度 30% + 准确度 35% + 节奏 25% + 流利度 10%
```

| 维度 | 权重 | 说明 |
|---|---:|---|
| 完整度 | 30% | 是否漏读、多读、少读 |
| 准确度 | 35% | 长音、促音、拨音、清浊、拗音等专项规则 |
| 节奏 | 25% | mora 时长是否合理，是否读满拍 |
| 流利度 | 10% | 异常停顿、重复、语速过慢 |

评分原则：

- 第一阶段以反馈可解释为优先，不追求绝对客观分数。
- 对低置信度错误使用“可能”“建议”措辞。
- 避免因为 ASR 误判给用户强负反馈。
- 分数主要用于用户自我对比和重练激励。

## 9. 页面设计

### 9.1 跟读练习页

核心元素：

- 日语句子
- 假名
- 中文释义
- 标准音播放
- 录音按钮
- 重录按钮
- 提交评测按钮

页面目标：

```text
让用户快速完成一次“听标准音 → 跟读 → 提交”的闭环。
```

### 9.2 评测结果页

核心元素：

- 总分
- 四项分数：完整度、准确度、节奏、流利度
- 句子高亮
- 错误列表
- 我的录音播放
- 标准音播放
- 再练一次

错误高亮建议：

| 状态 | 展示 |
|---|---|
| 正确 | 普通文本 |
| 轻微问题 | 黄色高亮 |
| 明显问题 | 红色高亮 |
| 漏读 | 下划线或缺失提示 |

### 9.3 错音复习页

核心元素：

- 高频问题统计
- 长音专项
- 促音专项
- 拨音专项
- 清浊音专项
- 推荐练习句

页面目标：

```text
把单次评测结果沉淀为长期学习路径。
```

## 11. 迭代计划

### P0：最小闭环

- 固定句子跟读
- 标准音播放
- 用户录音上传
- faster-whisper ASR
- 目标文本与识别文本比对
- 总分
- 漏读、错读、多读反馈

### P1：日语专项纠音

- pyopenjtalk 生成假名、mora 信息
- 长音检测
- 促音检测
- 拨音检测
- 基础拍节奏评分
- 错误高亮

### P2：专项增强

- 清浊音检测
- 拗音检测
- 用户错音画像
- 专项复习推荐
- 反馈模板优化

### P3：高级能力

- 高低重音检测
- F0 音高曲线分析
- 更精细的音素评分
- 开放式 AI 对话后评测

## 12. 主要风险与应对

| 风险 | 说明 | 应对 |
|---|---|---|
| ASR 短句识别不稳定 | 学习者发音不准时，ASR 容易误识别 | 不只依赖 ASR，结合目标文本和 forced alignment |
| MFA 部署复杂 | 需要准备模型、词典和环境 | MVP 先用 WhisperX 或粗时间戳，P1 再引入 MFA |
| 日语无空格 | 词边界处理复杂 | 第一阶段以假名/mora 为主，不强依赖分词 |
| 阈值难调 | 长音、促音时长因语速不同而变化 | 使用相对时长，不使用固定绝对阈值 |
| 反馈误判影响信任 | 错误纠音会挫伤用户 | 低置信度反馈使用建议语气，并允许用户重录 |
| 标准音质量影响体验 | TTS 不自然会影响模仿 | 优先使用真人录音或高质量预生成音频 |

## 13. 第一阶段成功标准

上线后重点验证：

- 用户能否顺利完成跟读评测闭环。
- 错词/错拍反馈是否能被用户理解。
- 长音、促音、拨音反馈是否有感知价值。
- 用户是否愿意重复练习同一句。
- 用户是否能通过二次重练提升分数。

建议核心指标：

| 指标 | 目标 |
|---|---|
| 首次评测完成率 | > 70% |
| 单句重练率 | > 35% |
| 反馈有用率 | > 60% |
| 二次练习分数提升率 | > 50% |
| 录音识别失败率 | < 10% |

## 14. 总结

第一阶段建议采用：

```text
faster-whisper + Silero VAD + pyopenjtalk + MFA/WhisperX + 规则引擎
```

产品上优先做固定句子跟读，技术上优先解决日语学习中最常见、最容易解释的发音问题：

- 长音
- 促音
- 拨音
- 清浊音
- 拗音
- 拍 mora 节奏

这套方案云 API 成本低，可本地部署，工程复杂度可控，并且能为后续高低重音、开放式对话和更专业的发音评分积累用户录音与错音数据。
